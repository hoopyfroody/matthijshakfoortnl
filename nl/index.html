Agents schrijven alle code waar je om vraagt. Weten waar je om moet vragen is het lastige deel.

Uitzoeken wat er gebouwd moet worden, bepalen wat ‘goed’ betekent, en de agent en de mensen helpen beslissen welke code een mens nog moet lezen. Dat zijn de verantwoordelijkheden van een Product Engineer. Ik doe dat werk in je team, ik leer je team het zelf te doen, en ik help je de juniors op te leiden die het straks doen.

Wat is een Product Engineer?

Code schrijven werd goedkoop. Het werk dat een agent niet (goed) kan, werd dat niet, en daar is een Product Engineer verantwoordelijk voor:

  • Uitzoeken wat gebruikers en klanten echt nodig hebben
  • Dat omzetten in een spec waar een agent mee kan bouwen
  • Bepalen wat ‘goed’ en ‘een plezier om te gebruiken’ is, en dat controleren
  • Beslissen welke risico’s je accepteert en welke afwegingen je maakt
  • Bepalen welke code een mens nog moet lezen voordat die live gaat

Kortom: het product- en engineeringwerk dat een mens nodig heeft. Ik denk dat deze rol onmisbaar wordt voor teams die goed met agents willen werken.

01 Hands-on Product Engineering

Ik bouw software die ondersteunt hoe je team werkt

Voor er agents waren, kostten veel ideeën voor maatwerksoftware te veel of duurde het te lang om ze te bouwen. Maar het punt waarop zulke tools zich terugverdienen is verschoven. Het dure deel is nog steeds het werk rond de code: uitzoeken wat het proces echt nodig heeft, de spec schrijven en de controles bouwen.

Bij het integreren van een LLM: gewone code doet alles wat gewone code kan. Het model krijgt alleen het deel waar het goed in is: oordelen en tekst begrijpen.

Tooling die je team efficiënter maakt

De juiste tooling haalt de frictie uit het werkproces van je team, zodat je team zijn tijd besteedt aan product engineering. Een deel daarvan moet je team nog steeds kopen, maar het omslagpunt is verschoven. Meer software kan nu specifiek zijn voor je team of bedrijf, en dat deel bouw of richt ik in.

Je team koopt

  • De coding agent zelf
  • Een gehoste AI-reviewdienst
  • Hosting en sandboxes voor agents op de achtergrond
  • LLM-observability
  • Preview-deployments

Ik bouw of richt in

  • Instructiebestanden en projecttemplates
  • Skills voor terugkerend werk: releases, migraties, incidentnotities, specs omzetten naar tickets, en nog veel meer
  • Hooks die voorkomen dat de agent ontspoort: formatting, geblokkeerde commando’s, beschermde paden
  • Eigen linters en structurele tests
  • Het reviewbeleid (welke code een mens leest) en een reviewer die het toepast
  • Eval-sets en CI-gates
  • Interne MCP-servers en CLI’s voor jullie eigen systemen
  • Een raamwerk voor continue verbetering

Die tooling ondersteunt je team en zorgt dat het op deze nieuwe manier blijft werken als ik weg ben. Het doel is mezelf overbodig te maken.

Zelf bouwen of niet?

Kleine tools zijn goedkoop geworden om te bouwen. Eigenaar zijn ervan niet. Drie vragen helpen je te bepalen wat je doet.

Zijn mensen ervan afhankelijk?

Kan het belangrijke data wijzigen of blootleggen?

Ligt het werk stil of loopt het flink vertraging op als het verdwijnt?

Beantwoord de drie vragen om te zien wat het nodig heeft.

Na de overdracht

Je eigen mensen worden eigenaar van de software. Ze krijgen de tests, een geschreven spec, de conventies en, als er een LLM in zit, een eval-set, zodat de volgende persoon of agent er veilig in kan werken. Je team beheert het. Ik blijf graag bereikbaar voor de momenten dat ze een second opinion willen.

Typische opdracht
Eén of twee dagen per week, drie tot zes maanden lang. Ik bouw één procestool, van het eerste gesprek met gebruikers tot de overdracht, en daarna zijn je eigen mensen de eigenaar.
Casus
Softwarebedrijf, ongeveer 30 developers, elke één à twee weken een release. Iemand was per release ongeveer vier uur bezig om ieders release notes om te zetten in één consistent opgemaakte lijst. Ik bouwde een systeem dat de notes van elke developer reviewt (en ze vriendelijk aanspoort om ze te verbeteren) en ze samenvoegt tot een voorstel voor de lijst. Het samenstellen van de lijst ging naar ongeveer een uur. En als behoorlijk groot bijkomend voordeel moesten de developers nadenken over het probleem dat ze oplosten, de oplossing en de impact. Dat verbeterde zowel de kwaliteit van de notes als de mindset van de developers.

02 Product Engineers vormen

Je eigen mensen groeien in de rol

Training, coaching en het goede voorbeeld geven. Dat voorbeeld geef je tijdens het werk zelf, dus dit begint vaak als hands-on werk. Drie dingen gaan vaak mis als teams op deze nieuwe manier gaan werken, en ik coach je team om ze te voorkomen:

  • De agent laten begrijpen wat je bedoelt. De agent bouwt iets goeds, maar niet wat je bedoelde, vaak omdat niemand de agent helder kon uitleggen wat de gebruiker echt wil.
  • AFK-agents of human-in-the-loop? Uren of zelfs dagen kwijt omdat een agent de bedoeling van de gebruiker verkeerd begreep, of aan meekijken bij agents die dat niet nodig hadden. Het juiste niveau van automatisering kiezen is lastig.
  • Apps onderhoudbaar houden voor mens én agent. De agent bouwt iets dat perfect werkt, maar de mens begrijpt het niet. De mens maakt handmatige wijzigingen die de agent daarna als heilig beschouwt, en dat hindert al het werk dat volgt.

Eén loop voor elke wijziging

  1. Praat met de gebruiker en schrijf de spec waar de agent mee bouwt.
  2. Schat in hoe groot de schade van een fout kan zijn: laat de agent alleen werken of blijf erbij, en kies de code die een mens leest.
  3. Leg elke conventie vast die het werk opleverde, voor mensen en agents.

Ik draai deze loop met je team tot hij zonder mij draait.

Typische opdracht
Eén of twee dagen per week met één team, drie maanden lang. Eerst doe ik het werk en kijken zij mee, daarna doen zij het en coach ik.
Casus
Vorige werkgever, als software architect. Ik onderzocht hoe het team coding agents goed kon inzetten. Ik gaf presentaties en schreef werkinstructies en tooling: een editor-workflow, manieren van werken met tests, en gedeelde skills. De editor-workflow wordt nog dagelijks gebruikt. De skills zijn vervangen door nieuwere, en dat is precies hoe de loop hierboven hoort te werken.

03 Juniors opleiden

Waar komen je seniors over vijf jaar vandaan?

Juniors leerden het vak door code te schrijven op basis van strak afgebakende tickets. Dat werk doen agents nu, dus wie juniors op tickets traint, traint ze voor het werk dat agents al doen.

Heb je al juniors? Nu agents de tickets coderen, hebben ze ander werk nodig om echt te groeien, en een team dat is ingericht om ze dat te geven.

Ik laat ze beginnen met het werk dat agents niet kunnen: praten met gebruikers en klanten, specs schrijven, test seams kiezen, inschatten hoe groot de schade van een fout kan zijn. Ze lezen en draaien code vanaf dag één, via de spec die ze zelf schreven en de tests die daarop controleren. Zelf code schrijven voor de kritieke delen leren ze later.

Ik help ook het team eromheen in te richten: waar juniors mee beginnen, met wie ze praten en hoe hun specs worden gereviewd. Je seniors reviewen de werkwijze en het proces van een junior net zo goed als de code.

Een sollicitatie die de juiste dingen test

  1. Een gesprek van 20 minuten met een ‘gebruiker’, gespeeld door iemand uit je team.
  2. Op basis daarvan schrijft de kandidaat een spec van één pagina.
  3. Een review van code die een agent op basis van die spec bouwde.

Waar ik op let

  • Ze vragen ‘waarom’ en ‘voor wie’ voordat ze ‘hoe’ vragen.
  • Ze schrijven helder.
  • Ze merken het als iets niet klopt in een demo.
  • Ze praten makkelijk met mensen die geen developer zijn.
  • Ze lezen code kritisch.
Typische opdracht
Je volgende wervingsronde voor juniors. Ik ontwerp de opdracht en zit bij de sollicitatiegesprekken, daarna coach ik de nieuwe collega drie maanden lang één dag per week.
Ervaring
Ik heb door de jaren heen flink wat juniors begeleid. Onlangs nam ik er een paar mee langs deze route in plaats van de ouderwetse. De eerste resultaten zijn veelbelovend.

Achtergrond

Ik bouw al meer dan vijftien jaar software, recent als software architect, vooral in TypeScript, vooral in teams van vijf tot vijftien mensen. De delen van dat werk die agents niet doen (requirements-interviews, domeinmodellering, bepalen welke tests een wijziging nodig heeft, beoordelen of iets goed is en of het een plezier is om te gebruiken) zijn de delen die me altijd het meest hebben beziggehouden. Ze houden me ook met beide benen op de grond nu de tools om de paar maanden veranderen.

Waarschijnlijk geen goede match als

  • je een vaste prijs wilt zonder verkennende fase;
  • je developers tien keer zo snel wilt maken;
  • je een kleine no-code-koppeling nodig hebt.
